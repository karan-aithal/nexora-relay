# Phase 1 walkthrough — ISO 8583 codec and acquiring host simulator

## 1. Design rationale

Phase 1 builds two things: a message codec (`OpenForecourt.Iso8583`) and a TCP acquirer
simulator (`OpenForecourt.HostSimulator`). Both are shaped by one fact stated up front in
`docs/protocol-iso8583.md`: **there is no single "ISO 8583 on the wire"**. The standard
fixes the message shape; every acquirer picks its own length encodings, numeric
representations and reserved-field usage. So the codec is *data-driven* over a *documented
dialect*, OFC-87, and the document was written before the code.

### The codec

- **`FieldDefinition`** is one row of the field table: number, name, type
  (Fixed/LLVAR/LLLVAR), length, encoding (numeric/alphanumeric/binary), and a `Sensitive`
  flag. **`Iso8583Dialect`** is a table of these; `Ofc87` is the one dialect that exists.
- **`FieldCodec`** encodes/decodes *any* field from its row. There is no per-field code.
- **`Bitmap`** is the presence map: two 64-bit halves, bit 1 signalling a secondary bitmap.
- **`Iso8583Message`** is immutable after `Build()`, indexer access, `TryGetField`, and a
  `ToString()` that renders a field-by-field trace with the PAN masked.
- **`Iso8583Codec`** ties it together: `Encode` (trusted, cannot fail) and `TryDecode`
  (untrusted, returns `Result<Iso8583Message, CodecError>`, never throws).
- **`Iso8583Framing` / `Iso8583FrameReader`** handle the 2-byte big-endian length prefix
  over a `PipeReader`, coping with partial and coalesced reads.

### The host simulator

Three layers (ADR 0005): `HostEngine` decides (pure, returns a `HostDecision` whose latency
is a value and whose silence is a null response), `HostServer` transports (one task per
connection, the only layer that sleeps or sockets), `HostLedger` records (lock-free, keyed
on terminal id + STAN for duplicate detection and reversal).

## 2. The three hardest parts, line by line

### 2.1 The bitmap, nibble by nibble

The bitmap is where hand-written ISO 8583 codecs go wrong, because the bit order is the
opposite of what most programmers reach for: **bit 1 is the *most significant* bit of byte
0**, and **bit 1 is not a field** — it means "a secondary bitmap (fields 65..128) follows".
Note that field 55 does *not* need a secondary bitmap: it is bit 55, well inside the primary
half. Only fields above 64 — here fields 70 and 90 — trigger the secondary.

In `Bitmap.Mask`:

```csharp
private static ulong Mask(int bitWithinHalf) => 1UL << (64 - bitWithinHalf);
```

Bit *n* is `1 << (64 - n)`. Bit 1 is `1 << 63` — the top bit. That single line is the whole
"most significant bit first" convention.

**A no-secondary case, exactly as the unit test pins it.** Fields 2, 3, 4, 11, 41, 49, none
above 64 (`BitmapTests.No_fields_above_64_means_no_secondary_bitmap`):

- Byte 0: bits 2,3,4 → `0100 0000 | 0010 0000 | 0001 0000` = `0111 0000` = **0x70**. Bit 1
  is clear: no field above 64, so no secondary bitmap.
- Byte 1 (bits 9–16): bit 11 is the third bit → `0010 0000` = **0x20**.
- Bytes 2–4: nothing → `00 00 00`.
- Byte 5 (bits 41–48): bit 41 is the first bit → `1000 0000` = **0x80**.
- Byte 6 (bits 49–56): bit 49 is the first bit → `1000 0000` = **0x80**.
- Byte 7: nothing → `00`.

Result: `70 20 00 00 00 80 80 00` = `"7020000000808000"`, exactly what the test asserts.
`WriteTo` emits this with one call because the whole half is a `ulong`:

```csharp
BinaryPrimitives.WriteUInt64BigEndian(destination, _primary);
```

Big-endian is what puts bit 1 (the top bit of the `ulong`) into the first byte.

**The secondary case, from the demo's reversal.** The reversal carries fields 3, 4, 7, 11,
41, 49 and **90**. Field 90 is above 64, so `ForFields` sets bit 1 and emits a secondary
bitmap; the demo prints `B2200000008080000000004000000000` (16 bytes). Byte 0 =
`1011 0010`:

- bit 1 = 1 (secondary follows) → `1000 0000`
- bit 3, bit 4 → `0010 0000 | 0001 0000`
- bit 7 → `0000 0010`

= `1011 0010` = **0xB2**. The secondary half covers fields 65..128, so field 90 is bit
`90 - 64 = 26` within it: byte 3 of the secondary (bits 89..96), and 90 is the second of
those → `0100 0000` = **0x40**, giving `00 00 00 40 00 00 00 00`. That matches the printed
tail `0000004000000000`.

Reading is the mirror: `TryRead` reads the primary `ulong`, and only if
`(primary & Mask(1)) != 0` does it read a second 8 bytes — that is how bit 1 drives whether
the frame is 8 or 16 bytes of bitmap. `PresentFields()` then iterates bits **2..128**, never
1, so the "bit 1 is not a field" rule is enforced in one place.

### 2.2 Framing: one reader that survives any TCP split

TCP is a byte stream. A single `read` can return half a length prefix, or three whole
messages, and the split is chosen by the network. `Iso8583FrameReader.ReadFrameAsync` is the
only code that knows this. The core is the interplay with the pipe's `AdvanceTo(consumed,
examined)`:

```csharp
case ParseOutcome.Frame:
    _reader.AdvanceTo(buffer.Start, buffer.Start);   // consumed through the frame
    return new FrameResult(FrameStatus.Frame, body, null);
...
default: // NeedMoreData
    _reader.AdvanceTo(buffer.Start, buffer.End);      // consumed nothing, examined all
    break;                                            // loop; next ReadAsync waits for more
```

The two `AdvanceTo` calls are the whole trick:

- On a **frame**, `TryParseFrame` has already sliced `buffer` past the frame it returned, so
  `buffer.Start` is the first byte *after* it. Passing that as `consumed` keeps every
  trailing byte buffered — which is exactly why three coalesced messages are read as three
  frames without losing the tail (`Reads_three_frames_coalesced_into_one_buffer`).
- On **need-more-data**, consuming nothing but marking everything *examined* tells the pipe
  not to hand back the same short buffer; the next `ReadAsync` blocks until more bytes
  arrive. That is what makes the byte-at-a-time test terminate instead of spinning
  (`Reads_a_frame_delivered_one_byte_at_a_time`).

The oversized-prefix guard runs **before** any body is buffered:

```csharp
if (length > MaxBodyLength) { error = ...; return ParseOutcome.Error; }
```

so a peer announcing a 65535-byte frame cannot make the process allocate that buffer
(`An_oversized_length_prefix_is_rejected_without_buffering_the_claim`). And there is a
subtle lifetime bug avoided here: the truncated-stream diagnostic captures `buffer.Length`
into the `FrameResult` **before** calling `AdvanceTo`, because the buffer's memory may be
recycled the instant it is advanced.

### 2.3 The engine: latency and silence as values, not sleeps

`HostEngine.Handle` returns a `HostDecision(Response, Latency, Note)`. The two things that
make a host worth testing a terminal against — slow responses and no response — are a
`TimeSpan` and a `null`:

```csharp
if (Rules.NoResponsePans.Contains(pan, StringComparer.Ordinal))
    return new HostDecision(null, latency, "no response injected for this PAN");
```

Because these are values, `HostEngineTests.Latency_is_returned_as_a_value_not_slept` asserts
that a configured 1.5s extra latency shows up as `TimeSpan.FromMilliseconds(1525)` — in
microseconds, with no waiting. Only `HostServer` turns the value into a real delay.

Reversal is the one read-modify-write on shared state, and it is a compare-and-swap, not a
lock:

```csharp
while (_entries.TryGetValue(key, out var existing)) {
    if (existing.Reversed || existing.ResponseCode != HostResponseCodes.Approved) return false;
    if (_entries.TryUpdate(key, existing with { Reversed = true }, existing)) {
        reversedMinor = existing.AmountMinor;
        return true;
    }
}
```

`TryUpdate` only succeeds if the entry has not changed since the `TryGetValue`, so two
racing reversals of one original cannot both return the money — the second sees
`Reversed == true` and answers 21. Duplicate detection is the same idea on the insert path:
`TryRecord` is `TryAdd`, so exactly one of N terminals sharing a STAN wins, which
`Many_concurrent_terminals_never_double_authorise_a_shared_stan` proves over real TCP.

## 3. What was rejected and why

- **An existing ISO 8583 library.** The deliverable is demonstrating a bitmap parser the
  author can explain line by line; a dependency hides exactly that. (ADR 0004)
- **Per-field parsing (`switch` on field number).** Does not port to a second dialect,
  concentrates bugs. Replaced by the data-driven table. (ADR 0004)
- **Throwing on malformed input.** Every decode input is untrusted; a bad frame is an
  expected outcome, so `TryDecode` returns a `Result` with an offset and diagnostic. (ADR
  0004, CLAUDE.md §6)
- **One class for decode+decide+delay+write.** Would make timing behaviour testable only by
  waiting. Split into engine/server/ledger. (ADR 0005)
- **A property-testing package.** A seeded `Random` generator buys reproducibility (the
  failing case is regenerated from the seed printed in the assertion) without a dependency,
  and understanding the ~30-line generator is part of the exercise.
- **A generic long-digit-run PAN-leak scan.** Field 4 (12 digits) and field 90 (42 digits)
  are legitimate digit runs; a shape scan false-positives. The leak test asserts the exact
  cleartext PAN values never appear.

## 4. Self-quiz

1. In the primary bitmap, which byte and which bit within it represents field 41, and why is
   it the *most* significant bit of that byte rather than the least?
2. `AdvanceTo` takes a `consumed` and an `examined` position. What breaks if, on a
   need-more-data path, you pass `buffer.End` as `consumed` instead of `buffer.Start`?
3. The reversal path uses `ConcurrentDictionary.TryUpdate` in a loop. What exact interleaving
   of two concurrent reversals is this defending against, and what does the loser observe?
4. Field 55's length prefix counts bytes, but field 2's counts characters. Where in the code
   is that distinction expressed, and why does it not matter for any field other than 55?
5. Why does `TryDecode` return a `Result` while `Encode` simply returns `byte[]` — what makes
   the two directions have different failure models?

## 5. Known weaknesses

- **OFC-87 is simpler than a real acquirer link.** ASCII rather than packed BCD, no MAC
  (field 64/128), no EBCDIC. All noted in `docs/protocol-iso8583.md` under "deliberately not
  implemented".
- **`SPEC-UNVERIFIED` fields.** Field 22 (n 3 vs n 12 across ISO revisions), field 49 (a 3
  vs n 3), field 55 (reserved in 1987; EMV-in-55 is convention), and the field 90 layout are
  pinned by choice, not verified against the 1987 text. Marked in code and document.
- **Trailing-space ambiguity in fixed `ans` fields.** A value whose own last character is a
  space is indistinguishable from padding. The codec keeps the round trip exact by storing
  the padded form on both sides; it does not recover "intended" trailing spaces. Documented
  in `RoundTripPropertyTests`.
- **`HostServer` still uses a real `Task.Delay` for injected latency.** The engine's timing
  is fully testable; the server's application of it is covered only by wall-clock TCP tests
  with generous timeouts. An `IClock`-driven server delay would remove the last real waits.
- **The `HostClient` is serial request/response.** It is a diagnostic tool, not the
  production `IHostConnection` adapter, which must multiplex and correlate replies to
  requests on STAN (including discarding a reply whose request already timed out). That
  arrives with the OPT in a later phase.
- **No store-and-forward, no stand-in.** A host that is down means the transaction fails
  now; the RabbitMQ store-and-forward path is Phase 5.
